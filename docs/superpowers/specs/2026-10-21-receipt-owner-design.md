# 領収書に会員IDを持たせ、会員画面を本人の領収書だけにする（Issue #43）

- 作成日：2026-10-21
- 対象 Issue：#43「会員画面の「マイ領収書」で、同じクラブの他の会員の領収書も見える・印刷できる」
- 状態：設計承認済み（実装前）

## 1. 背景と目的

会員画面の領収書は、どれも「自クラブの領収書すべて」を対象にしている。

| 画面 | パス | 今の絞り込み |
|---|---|---|
| マイ領収書（一覧） | `src/app/(public)/club/[slug]/my/receipts/page.tsx` | クラブ・発行済み・未削除 |
| マイ領収書（印刷） | `src/app/(public)/club/[slug]/my/receipts/[receiptId]/print/page.tsx` | クラブ・発行済み・未削除（#41 で追加） |
| 会員トップページ | `src/app/(public)/club/[slug]/dashboard/page.tsx` | クラブ・未削除（取消済みも含む） |

そのため、同じクラブのほかの会員の領収書（氏名・金額）が見え、電子印鑑つきで印刷もできる。

領収書テーブル（`receipts`）には「誰の領収書か」を示す会員IDがない。本人との結び付けは、出欠記録（`attendance_id` → `attendances.user_id`）を経由するときしかたどれない。年会費の一括発行では出欠記録がなく、宛名（`receipt_name`）に名前の文字列が入るだけである。

**目的**：領収書に会員IDを持たせ、会員画面には本人の領収書だけを表示・印刷できるようにする。

## 2. データの変更（マイグレーション `migrations/0014_receipt_user_id.sql`）

### 2.1 列と索引

- `receipts.user_id TEXT NULL REFERENCES users(id)` を追加する
  - 空を許す。外部の参加者の領収書など、会員がいない領収書があるため
- 本人の領収書の検索用に `receipts(user_id)` の索引を追加する
- `src/lib/db/schema.ts` の `receipts` に `userId: text('user_id').references(() => users.id)` を追加する

### 2.2 既存データの埋め戻し（同じ SQL の中で行う）

何度実行しても結果が変わらないよう、`user_id IS NULL` の行だけを更新する。

1. **出欠から発行した領収書**：`attendance_id` が入っている領収書に、その出欠記録の `user_id` を入れる（出欠記録の例会が領収書と同じクラブのものに限る。手入力発行の判定と同じ）
   - 外部の参加者の出欠記録は `user_id` が空なので、領収書も空のまま
2. **年会費の領収書**：次の条件をすべて満たす候補が**ちょうど1人**のときだけ、その会員IDを入れる
   - 領収書が `attendance_id` なし、かつ但し書きに「年会費」を含む
   - 年会費レコード（`annual_fees`）が、領収書と同じクラブにあり、支払済み（`payment_status = 'paid'`）で、削除されていない
   - その年会費レコードの会員名（`users.name`）が、領収書の宛名（`receipt_name`）と完全に一致する
   - 領収書の但し書きに、その年会費レコードの年度（`fiscal_year`）が含まれる
   - 候補が0人または2人以上（同姓同名など）の領収書は空のまま残す
3. 上記以外の領収書（手入力で出欠記録の指定なし、など）は空のまま残す

### 2.3 適用後の確認用 SQL

マイグレーションとは別に、PR の本文に次を確認する SQL を載せる。

- 種類別（出欠由来／年会費／その他）の、会員IDが入った件数と空の件数
- 年会費の領収書のうち、結び付けられなかったものの一覧（宛名・クラブ・但し書き）

## 3. 発行時に会員IDを記録する

領収書を作る処理は次の3か所で、それぞれ `user_id` を記録する。

| 発行のしかた | 場所 | 記録する会員ID |
|---|---|---|
| 出欠からの一括発行 | `src/app/api/receipts/bulk/route.ts`（出欠モード） | 出欠記録の `user_id`（外部の参加者は空） |
| 年会費の一括発行 | `src/app/api/receipts/bulk/route.ts`（`annual_fee` モード） | 年会費レコードの `user_id` |
| 手入力での発行 | `src/app/api/receipts/route.ts`（POST） | 出欠記録を指定したときだけ、その出欠記録の `user_id`。指定がなければ空 |

- 手入力の画面（`ReceiptsList.tsx`）は変更しない
- 手入力で指定された出欠記録は、発行するクラブのものであることを確認してから会員IDを使う（他クラブの出欠記録で他人に結び付けないため）

## 4. 会員画面の表示

本人の領収書を表す条件を1つの関数にまとめ、3つの画面で使う。

- 条件：`receipts.user_id = ログイン中の会員ID` かつ `status = 'issued'` かつ `deleted_at IS NULL`
- 置き場所：`src/lib/receipts/` 配下（例：`ownReceiptsCondition(userId)`）
- 対象：マイ領収書の一覧・件数・印刷ページ、会員トップページの領収書
  - 会員トップページは、今は取消済みも表示しているが、ほかの会員画面とそろえて発行済みだけにする
- 印刷ページで本人の領収書でないものは 404 にする（存在が分からないように）
- クラブの条件（`club_id`）は、念のため今までどおり併せてかける
- 会員IDが空の領収書は会員画面に出ない。管理画面では今までどおり扱える

## 5. リリースの順番（必須）

新しいコードは `receipts.user_id` に書き込む。列がない DB で動くと、領収書の発行がエラーになる。

1. 本番の Supabase に `migrations/0014_receipt_user_id.sql` を適用する（SQL Editor など）
2. 確認用 SQL で、埋め戻しの件数を確かめる
3. PR をマージする（本番に自動デプロイされる）
4. デプロイ完了後に、同じマイグレーションをもう一度実行する。1〜3 の間に旧コードが会員IDなしで発行した領収書を結び付けるため（何度実行しても問題ない）。確認用 SQL で件数をもう一度確かめる

PR の本文にこの手順を書く。
